# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**ValueBet** — a sports betting analytics dashboard. Shows upcoming football and basketball fixtures with team stats, and highlights value bets by comparing bookmaker odds against Pinnacle's sharp lines.

## Running the app

Two processes must run concurrently:

```bash
# Frontend (React + Vite, port 5173)
npm run dev

# Backend (Express, port 3001) — in a separate terminal
cd backend && npm run dev
```

Build for production:
```bash
npm run build   # outputs to dist/
```

## Architecture

### Frontend (`src/`)
React 18 SPA built with Vite. Vite proxies all `/api` requests to `http://localhost:3001`.

**Routing** (`App.jsx`): Sidebar + `<Routes>` for `/football`, `/football/:id`, `/basketball`, `/basketball/:id`.

**Data sources — two parallel tracks:**
1. **Static fixture data** (`src/utils/fixtures.js`, `src/utils/basketball.js`): hardcoded match data used by the current UI pages. This is what the pages actually render.
2. **Live API utilities** (`src/utils/api.js`): fetch functions for the backend APIs. Exist but not yet wired into the main pages.

**Key components:**
- `OddsTable.jsx` — renders h2h and BTTS odds per bookmaker, highlights best odds and value edges vs Pinnacle
- `StatBar.jsx` — side-by-side comparative stat bar for match detail pages
- `FormStrip.jsx` — W/D/L recent form badges
- `TeamLogo.jsx` — loads logos from API-Sports CDN: `https://media.api-sports.io/football/teams/{logoId}.png`

All dates/numbers are formatted in French locale (`fr-FR`) via `src/utils/formatters.js`.

### Backend (`backend/server.js`)
Single Express file. All external API calls happen here; the frontend never calls third-party APIs directly.

**Routes:**
- `GET /api/health`
- `GET /api/fd/results` — final scores for the 5 leagues, ±2/1 day window (`_getFdLeaguesResults()`, 60s cache). Sole purpose: settlement (`resolveCompletedFootballAlerts()` frontend + `runAutoSettle()`/near-miss backend) — `/api/fd/matches` below never returns finished matches (`?status=SCHEDULED`), so this is a separate route on purpose. **Despite the route/function name, this is api-football since 2 septembre 2026** — see "Session 2-4 septembre" below. Kept the `fd`-prefixed name to avoid touching every frontend call site for a backend-only source swap.
- `GET /api/fd/matches` — next 5 fixtures + standings for 5 leagues + Brasileirão. 60s cache (shortened from 30min on 3 septembre). Sole source for the 5-league fixture list (Carte du Monde hub, `WorldMapPage.jsx`, and `MatchDetailPage.jsx` via `useFootballFixtures.js`). History: football-data.org-only until 12 juillet 2026 → API-Football removed entirely → **reintroduced 22 juillet 2026** as an injuries/xG/snapshot supplement only → **fully migrated to api-football (fixtures, standings, results, live status) on 2 septembre 2026** for `FB_MIGRATED_LEAGUES = ['ligue1','pl','laliga','bundes','seriea','bresil']` (`fetchApiFootballLeagueBundle()`, see "Session 2-4 septembre" below) — football-data.org now only serves the CDM (`/api/fd/worldcup`, competition over) and 2 rare single-match fallback routes (`/api/fd/match/:id`, `/api/fd/resolve-legacy-id`). `FD_API_KEY`'s 10 req/min quota is effectively unused day-to-day now — the Dashboard's FD quota gauge showing "—" is this, not a bug.
- `GET /api/odds` — h2h + btts, foot toutes ligues confondues. Malgré le nom (hérité), ne passe plus par The Odds API depuis longtemps (constantes `ODDS_SPORTS`/`ODDS_API_KEY` retirées le 9 septembre 2026, code mort — jamais réellement appelées) : `_refreshOddsCacheInner()` scrape directement Unibet/Betclic/Winamax/Pinnacle (`_mergeFootballBookmaker`), `allMatches` démarre vide et se construit entièrement depuis ces 4 scrapers.
- `GET /api/alerts` — value bet alerts: edges above `VALUE_THRESHOLD` (default 2%).
- `GET /api/nba/scoreboard` — ESPN live NBA scoreboard. Polled every 30s if live game active, 5min otherwise.
- `GET /api/nba/players/:teamId` — ESPN roster for a team. Cache 6h.
- `GET /api/nba/teamschedule/:teamId` — ESPN team schedule (recent + upcoming games). Cache 6h.
- `GET /api/nba/playergamelog/:playerId` — ESPN player game log (last ~15 games). Cache 6h.
- `GET /api/nba/boxscore?date=ISO&home=ABR&away=ABR` — ESPN box score for a completed game. Cache 5min (to pick up NBA post-game stat corrections). Date converted UTC→ET. Response keys use standard abbreviations (SAS, NYK…).
- `POST /api/basketball/result` — team win probability via `computeTeamWinProb` (see below). Body: `{homeGames, awayGames, gameDate, round, league, homePlayers, awayPlayers}`. Used both by `generateBackgroundAlerts()` (alerts) and `BasketballDetailPage.jsx`'s "Modèle 1X2" widget (display) — same function, single source of truth.
- `GET /api/football/cdm/poolavg?fixtureId=fdcdm_xxx` — CDM pool average `avgGF`/`avgGA`. With `fixtureId`, returns the value **frozen** for that match (see CDM section below) if already generated; without it, the live current pool average.
- `GET /api/football/teamxgstats?league=X&team=Y&date=Z` — recent xG/xGA/shots/possession for a team via api-football Pro (see "api-football Pro" below). Returns `{found, xG, xGA, shotsPerGame, shotsOnTarget, possession, games}`.
- `GET /api/football/projections-snapshot/:fixtureId` — real backend-computed BTTS/O-U/1X2 for a fixture, frozen at first generation (see "Football snapshot" below). Returns `{found, bttsProb, pOver25, pUnder25, pHome, pDraw, pAway, lambdaHome, lambdaAway, estimated, savedAt}`.
- `GET /api/outrights` — competition-winner odds (Ligue 1, PL, La Liga, Serie A, Bundesliga, NBA, WNBA). `?refresh=1` forces a re-scrape (see Outrights section below).
- `GET /api/mlb/preview` — MLB fixtures + Betclic/Unibet Total runs odds + model probabilities per line, merged in one call (see "MLB" section below). `GET /api/mlb/lineups` — RotoWire confirmed/probable lineups. `GET /api/mlb/teams` / `GET /api/mlb/roster/:teamId` — MLB Stats API roster (Base de données page). `GET /api/mlb/games` / `GET /api/mlb/teamstats` / `GET /api/mlb/odds` / `GET /api/mlb/matches` — lower-level building blocks used internally by `/preview`.
- `GET /api/analysis/near-miss` — basketball player-props near-miss log (pts/reb/ast/3pts NBA+WNBA). `GET /api/analysis/near-miss-football` — football BTTS/O-U/Résultat near-miss log. `GET /api/analysis/near-miss-basket-markets` — basketball Résultat/Total O-U/Écart H2H near-miss log (NBA/WNBA/ACB/BBL/LegaA, added 24 juillet 2026, see "Near-miss tracking" below). `GET /api/analysis/near-miss-mlb` — MLB Total runs near-miss log, unfiltered (see "MLB" section below).

**Value bet calculation:**
```
fair_prob = (1/pinnacle_odds) / overround   // overround = sum of 1/odds for all outcomes
edge = bookmaker_odds * fair_prob - 1
```

**Player props alerts — ladder de lignes alternatives (18 juin 2026, `findLadderAlternative()` in `server.js`):**
For NBA/WNBA/EU basket player props (pts/reb/ast/tpm), each player normally gets evaluated on a single "reference" bookmaker line (`bks.unibet[stat] ?? bks.winamax[stat]`). When that line's probability+edge already clear the floor but its odds don't reach the `1.60` minimum on Unibet/Betclic, `findLadderAlternative()` searches the full line ladder already scraped for `PlayerLinesPage.jsx` (`bks.unibetAllLines[stat]` / `bks.betclicAllLines[stat]`) for a neighboring line in the direction that *raises* the odds on the favored side (higher line for Over, lower for Under). The probability is recalculated from scratch at each candidate line (never reused from the reference line) via the same `probAtLeast`/`displayProb` calibration; all the existing gates (floor, edge, WNBA reb-margin/ast-cap/tpm-min-avg, NBA L2-above-line) are re-checked against the candidate line too. Among candidates that pass both the odds and probability gates, the one with the **highest probability** wins. Resulting alerts carry `lineSource: 'ladder'` and use the alternate `line`/odds instead of the reference one — same one-alert-per-player-per-stat rule, just possibly on a different line than the one shown by default elsewhere in the UI. Applied at all 5 emission sites: NBA live + frozen, WNBA live + frozen, EU (acb/bbl/legaa).

**Player props — match-page display unified with the real alert engine (1er août 2026):** `BasketballDetailPage.jsx`'s "Analyse Props" section used to run its own hand-copied reimplementation of the probability model (local `computeEstimate`/`probAtLeast`/`calcStd` + ~20 factor helpers), which had drifted from the real backend model in `compute.js` (missing winsorization, missing the `roleShrunk` branch, never using real per-position opponent defense) — confirmed on a real case (Natasha Cloud showing 65% assists on the match page while the alert engine never even logged a near-qualifying attempt for her). Fixed the same way Résultat/Total/Spread already were: three new pure orchestration functions in `server.js` (`getPlayerProjectionsNBA`/`getPlayerProjectionsWNBA`/`getPlayerProjectionsEU`, placed after `runEUPropsAlerts()` and before `generateBackgroundAlerts()`) reuse the exact same real functions the alert engine calls (`computeEstimate`/`computeEUEstimate`, `displayProb`, `oppInjuryEffect`, `computeRedist`) — only the *live* computation path is replicated (not the frozen/snapshot path, since an on-demand page load always wants a fresh number), and deliberately **none** of the alert-decision logic (floors, season-margin gates, min-edge, ladder-alternate search, near-miss logging) — a display doesn't need to know if a number would clear an alert threshold. Exposed via `POST /api/basketball/player-projections` (same request/response shape family as `/result`/`/total`/`/spread`), called by `PropsSection` for `BACKEND_MODEL_LEAGUES = ['nba','wnba','acb','bbl','legaa']` instead of its local calc. `compute.js`'s `computeEstimate` also now returns a `factors` array (the same internal pace/defense/rest/etc. values it already computed, just exposed) to keep the "Facteurs du modèle" breakdown panel working with real numbers. **Euroleague and LNB keep the old local calculation unchanged** — neither has ever had a real backend alert engine for props (LNB excluded from `runEUPropsAlerts` for unreliable gamelogs, Euroleague never covered at all), so there is nothing to unify for them and zero regression risk there. Verified: 3/4 real players cross-checked against the live `bg-log` matched exactly (4th within 2%, live data refresh between calls, not a formula gap); zero lines changed inside `generateBackgroundAlerts()` or its 5 existing prop call sites (diff-reviewed); live alerts identical before/after.

**Basketball Résultat (victoire équipe) alerts — `computeTeamWinProb()` in `server.js` (19 juin 2026, replaces EarlyWin):**
EarlyWin (the old "team leads by +X or wins" alert) used an uncalibrated empirical formula (`P(EW) = 0.70×pWin + 0.15×(1-pWin)`) and was never actually wired to the frontend sync pipeline (`syncAlerts.js` had no handler for `type:'earlywin'` — the only alerts ever shown came from a separate, redundant client-side generator in `BasketballDetailPage.jsx`). Replaced end-to-end with an independent team-strength model:
- `computeTeamWinProb({homeGames, awayGames, gameDate, round, isWNBA, homeOutPenalty, awayOutPenalty})` — net rating (`ptsScored - ptsAllowed`, EWA-weighted) per team, adjusted by `getRestFactor`/`getScheduleDensityFactor` (from `compute.js`), `+HOME_COURT_PTS` (2.5, scaled to the league via the same point-scale rescale as EU), damped by `getPlayoffFactorTotalBg` in playoffs, converted to win probability via `tCDF4` (margin/std). `calcKeyPlayerOutPenalty()` removes `KEY_PLAYER_OUT_FACTOR=0.4` × season pts for any roster player with `injury==='Out'` and `stats.pts >= KEY_PLAYER_PTS (15)`.
- Generated in `generateBackgroundAlerts()` for NBA/WNBA (section 4b-bis) and EU acb/bbl/legaa (section 4b, schedules rescaled to NBA-point-equivalent like the EU props engine) — gated on the **h2h market** (not the old, rarer "earlywin/avance" market), `RESULT_ALERT_PROB = 0.80`, `RESULT_MIN_ODDS = 1.50`, bookmaker loop (`Object.entries(h2hBks)`) filters out winamax since 22 juin 2026 (same as basket props/total/football).
- Output: `type: 'basketball_result'` (`id: ${eventId}_{league}_result_{side}` for NBA/WNBA, `${eventId}_eu_result_{side}` for EU), `direction: 'home'|'away'`, `probability`, `margin` (expected point margin), `edge` vs vig-removed h2h odds.
- Frontend: `syncBasketballResultAlerts()` (`src/utils/syncAlerts.js`) merges into `basketball_result_alerts` localStorage key. `BasketballResultCard` (`PlaceBetPage.jsx`) renders pending cards.
- **Single source of truth**: `BasketballDetailPage.jsx`'s "Modèle 1X2" display widget calls `POST /api/basketball/result` with its already-fetched schedules/rosters — same function as the alert generator, so the page never shows a probability that disagrees with the alert (this exact kind of divergence, for a different bug, was the whole subject of the 19 juin session — see [[project_refonte_validation_watch]] memory).

**Basketball Total O/U — tendance H2H resserrée aux vraies séries (22 juillet 2026, `computeGameTotalFull()` in `server.js`):**
`h2hFactor` (added 22 juin for the ACB Barcelone-Valence playoff-series case: totals dropping game after game as defenses adjust) used to extrapolate a trend from any 2 head-to-head meetings in the season, regardless of how far apart in time they were. Real case: Seattle-Minnesota WNBA had only 2 meetings 6 weeks apart (6 juin, 156 pts → 21 juillet, 207 pts) — extrapolated into a wrongful +15% (capped) push on the 22 juillet rematch, which then collapsed to ~160 pts (alert lost). Fix: `H2H_SEQUENCE_MAX_DAYS = 14` — the trend now only extrapolates if the last H2H meeting is ≤14 days before the current game AND the 2 meetings used are ≤14 days apart (genuine series/back-to-back); otherwise `h2hFactor` stays neutral (1.0), same as the pre-existing default with <2 meetings. Single function shared by `game_total` alerts (NBA/WNBA/EU) and the `/api/basketball/total` display widget — one fix point, no divergence possible.

**Football BTTS / Over-Under alerts (`backend/computeFootball.js` + `generateBackgroundAlerts()` section 4d):**
Poisson model, generated every 20min alongside NBA/EU basket alerts — no need to visit `MatchDetailPage` for an alert to be created.
- `computeLambdas({homeGF, homeGA, homePlayed, awayGF, awayGA, awayPlayed, leagueAvgGoals, avgGF, avgGA, homeAdv=1.10})` — attack/defense factors normalized by `avgGF`/`avgGA` (falling back to `leagueAvgGoals` if omitted), each factor passed through `shrinkFactor()` (see below), λ rescaled by `leagueAvgGoals` × home advantage. Returns `null` if sample too small.
- `shrinkFactor(rawFactor, games, k=SHRINK_K=5)` (25 juin 2026) — pulls a small-sample attack/defense factor toward 1.0 ("average team") proportionally to `confidence = games/(games+k)`: at 3 games, only ~37% of the raw deviation from 1.0 is trusted; at 20 games, ~80%. Literature-style constant, not locally calibrated (same caveat as `DIXON_COLES_RHO` below) — mainly matters for CDM squads early in the tournament with only 3-4 real/qualifier matches on file. Mirrored client-side in `MatchDetailPage.jsx` (`computeCdmBTTS`, same `SHRINK_K`).
- **Dixon-Coles correlation** (25 juin 2026) — independent Poisson underestimates low, correlated scorelines (0-0, 1-0, 0-1, 1-1: a team protecting a lead closes the game down) relative to real results. `computeScoreGrid(λh, λa, rho=DIXON_COLES_RHO=0.10, kMax=10)` builds the joint P(i,j) grid, multiplies the 4 low-score cells by `dixonColesTau(x,y,λh,λa,rho)` (standard Dixon & Coles 1997 τ — reduces (0,0)/(1,1), boosts (0,1)/(1,0)), then renormalizes the whole grid to sum to 1. `ρ=0` reproduces the old independent-Poisson numbers exactly (validated to ~1e-7) — it's the safety net if this ever needs to be turned off. `ρ=0.10` is a textbook reference value, **not calibrated on our own results** (sample too small for a reliable MLE fit).
- `computeBTTSProb(λh, λa, rho=DIXON_COLES_RHO)` — sum of `computeScoreGrid` cells where `i≥1` and `j≥1` (replaces the old `(1-P(home=0))*(1-P(away=0))` closed form, which assumed independence).
- `computeOUProb(λh, λa, line, rho=DIXON_COLES_RHO)` — sum of grid cells where `i+j ≤ floor(line)` → `pUnder`, `pOver = 1-pUnder`. At the standard 2.5 line, the 4 Dixon-Coles cells all sit inside the same under-bucket, so the net effect on O/U is small; the correction mainly reshuffles BTTS and 1X2 draw probability.
- `compute1X2Probs(λh, λa, kMax=10, rho=DIXON_COLES_RHO)` — same grid, sums `P(i,j)` by `i>j` (home win), `i===j` (draw), `i<j` (away win) → `{pHome, pDraw, pAway}`. All three (BTTS/O-U/1X2) now derive from one shared grid for internal consistency.
- **Neutral home advantage — CDM only** (25 juin 2026): `homeAdv` is no longer a blanket `1.10` for World Cup fixtures. `CDM_HOST_NATIONS = new Set(['United States','Canada','Mexico'])` (2026 hosts) — `homeAdv: CDM_HOST_NATIONS.has(g.home.name) ? 1.10 : 1.0` is computed when building each CDM fixture and passed into `computeLambdas`; everything else (the "home" label is arbitrary fixture-list order at a neutral tournament venue) gets `1.0`. The 5 domestic leagues are unaffected (no `homeAdv` set on their fixture objects → `computeLambdas` default `1.10` applies, same as before). Mirrored in `MatchDetailPage.jsx` (`computeCdmBTTS`, `CDM_HOST_NATIONS`, 4th arg = `fixture.home.name`).
- Fixtures source: `_fdCache.matches` (5 leagues, `fixtureId = fd_${id}` — populated from api-football since 2 septembre 2026, see "Session 2-4 septembre" below, despite the `fd` naming, `leagueAvgGoals = FB_LEAGUE_AVG_GOALS[league]` — `{ligue1:1.35, pl:1.45, laliga:1.35, bundes:1.55, seriea:1.35}`, `avgGF`/`avgGA` omitted — closed league, GF≈GA on average, single constant is fine) + `_cdmCache.games` `STATUS_SCHEDULED` (`fixtureId = fdcdm_${id}`, `leagueAvgGoals = CDM_AVG_GOALS = 1.30`, `avgGF`/`avgGA` computed **dynamically** as the average `goalsFor`/`goalsAgainst` across all teams in the current CDM fixture pool — `CDM_AVG_GF=2.15`/`CDM_AVG_GA=0.78` are fallback-only if no stats available, requires `games >= 3` both teams via `/api/football/cdm/teamstats/:name`).
  - **Important**: `/api/football/cdm/teamstats/:name` returns `goalsFor`/`goalsAgainst` as already-weighted **per-match averages** (not totals). `computeLambdas` expects totals (it divides by `played`), so the CDM fixture builder multiplies back by `games`: `homeGF: hs.goalsFor * hs.games, homePlayed: hs.games`. Don't pass the raw averages directly — λ collapses to ~0 and every match falsely alerts "Under" at 100%.
  - **CDM attack/defense asymmetry**: qualified WC teams' recent friendlies/qualifiers are mostly against weaker opponents, so average GF is far above average GA across the squad pool. Normalizing both attack and defense by the same `CDM_AVG_GOALS=1.30` crushed every λ below 1.7 → 100% "Under" regardless of matchup. Fix: `avgGF`/`avgGA` normalize attack/defense separately, `CDM_AVG_GOALS` only rescales the final λ (home/away split + home advantage). The 5 leagues are unaffected (no `avgGF`/`avgGA` passed → same behavior as before).
  - **Dynamic avgGF/avgGA**: computed each `generateBackgroundAlerts()` run as the mean `goalsFor`/`goalsAgainst` over every team (`games >= 3`) appearing in the scheduled CDM fixtures — self-recalibrates as the team pool changes (knockout stage, new qualifiers) instead of relying on a stale hardcoded sample. A fixed `avgGA=0.65` (sample of ~13 teams) was initially used but proved too low once weaker teams (Haiti, Curaçao, NZ, Scotland — GA ~1.0-1.4) were included, inflating defense factors and producing unrealistic BTTS alerts (e.g. Germany vs Curaçao 75%). The dynamic average (~0.83 on the current pool) removed those overconfident BTTS calls entirely.
  - **Fix 18 juin 2026 — matchs CDM réels manquants des stats équipe**: `/api/football/cdm/teamstats/:name` ne récupérait que `fifa.friendly` + `fifa.worldq.{conf}` (amicaux + qualifs), jamais `fifa.world` (le calendrier de la Coupe du Monde elle-même). Une fois le tournoi commencé, les matchs de poule déjà joués (J1, J2…) étaient donc invisibles du modèle, qui continuait de tourner sur des amicaux/qualifs d'avant-tournoi (ex: Canada vs Qatar J2 calculé sans voir Canada 1-1 Bosnie ni Qatar 1-1 Suisse, leurs vrais matchs de poule précédents). Fix : ajout de `fetchEspnSoccerSchedule('fifa.world', espnId)`, résultats tagués `type: 'worldcup'`, poids `1.5` (au-dessus des qualifs `1.3` et amicaux `0.85`) — un match de poule réel est la donnée la plus représentative une fois le tournoi lancé (effectif et forme actuels, niveau d'adversité CDM).
  - **Note — alias nom manquant**: `ESPN_CDM` utilise `turkiye` (nom FIFA) mais la source `_cdmCache` (football-data.org) renvoie `Turkey` → 404 sur `/api/football/cdm/teamstats/Turkey`, cette équipe est donc exclue de la moyenne du pool et n'a pas d'alertes générées. Pas encore corrigé (ajouter `turkey: 'turkiye'` à `CDM_NAME_ALIASES` si besoin).
  - **Fix 19 juin 2026 — avgGF/avgGA figés par match (`freezeCdmPoolAvg()`)** : avant ce fix, `avgGF`/`avgGA` étaient recalculés à *chaque* cycle de 20min sur le pool de matchs encore programmés dans les 24h — un pool qui change constamment fait dériver fortement la probabilité d'un match déjà suivi, sans qu'aucune donnée de ce match lui-même ait changé (cas réel : BTTS Mexique-Corée du Sud généré à 76%, recalculé à 18% quelques heures plus tard, alors qu'aucune des deux équipes n'avait rejoué). Fix : `avgGF`/`avgGA` sont maintenant figés par `fixtureId` dès la 1ère génération (`_cdmFixturePoolAvg`, persisté dans `backend/cache/cdm_fixture_poolavg.json`), réutilisés tels quels aux cycles suivants tant que le match n'a pas eu lieu. Exposé côté frontend via `GET /api/football/cdm/poolavg?fixtureId=...` (`MatchDetailPage.jsx` l'utilise déjà).
- Alert thresholds: `FB_BTTS_ALERT_PROB = 0.70`, `FB_RESULT_ALERT_PROB = 0.70` (raised 27 juin 2026, see "Session 27 juin" below), `FB_BTTS_OU_MIN_ODDS = 1.60`, `FB_RESULT_MIN_ODDS = 1.50` (best of unibet/betclic on the proposed direction — winamax excluded from the threshold check since 22 juin 2026, same as basket props/total/result; winamax odds still shown on the card for reference). `FB_OU_ALERT_PROB = 0.75` (raised from 0.65 on 8 septembre 2026 — audit du 7 septembre sur near-miss : 84,1% de réussite réelle à ≥75% (n=113), jusqu'à 90,5% à ≥85% (n=21) ; marché confirmé le plus fiable de l'app à ce seuil). O/U tries line `2.5` then falls back to `1.5` (the 0.75 governs line 2.5 across every league, and the 1.5 fallback everywhere except the 5 Big Five leagues, which keep their own separately-calibrated `FB_BIG5_TOTAL15_PROB = 0.60` for that fallback, untouched by this change), one alert per fixture.
- Output: `type: 'football_btts'` (`id: ${fixtureId}_btts_yes`, same id scheme as the client-generated `fb_btts_alerts` → natural dedup), `type: 'football_total'` (`id: ${fixtureId}_total_${line}`, includes `estimated` = `λhome+λaway` expected total goals), and `type: 'football_result'` (`id: ${fixtureId}_result_${direction}`, `direction ∈ {home,draw,away}`, includes `probability` and optional `edge` vs vig-removed h2h odds).
- **Football Résultat 1X2 (15 juin 2026)**: each outcome (home/draw/away) is treated as an *independent binary yes/no proposition* (same framing as BTTS), not a 3-way mutually-exclusive pick — since `2 × FB_RESULT_ALERT_PROB > 1`, at most one outcome can qualify per fixture, so still "one alert per fixture". h2h odds come from the same scraping merge as BTTS/O-U (`_mergeFootballBookmaker` → `oddsMatch.markets.h2h.bookmakers[bk] = {home, draw, away}`), `FB_BOOKS = ['unibet','betclic']` (winamax_foot permanently blocked since 11 juin anyway, and explicitly removed from the threshold check on 22 juin 2026 — `?.[key] ?? 0` handled its absence gracefully before that too). Edge computed via `removeVig(pair, 'h2h')` when all 3 odds present from the chosen bookmaker.
- Frontend sync: `syncFootballAlerts()` (`src/utils/syncAlerts.js`) merges into `fb_btts_alerts` / `fb_total_alerts` / `fb_result_alerts` localStorage keys, preserving accepted/rejected. `BTTSAlertCard`/`FootballTotalCard`/`FootballResultCard` (shared in `src/components/FootballAlertCards.jsx`, with `FB_LEAGUE_META`) render `pending` cards in `PlaceBetPage.jsx`.

Comme `_euroCache` n'est jamais persisté sur disque, chaque redémarrage backend (fréquent en dev avec `node --watch`) le remettait à zéro, donc le prochain cycle bg-alerts refaisait ce calcul complet même en plein hors-saison (ACB/BBL/Lega A à 0 match programmé en juillet), pour un résultat jamais utilisé. Comportement identique quand il y a un match ; aucune autre section EU (Résultat/Écart H2H/Total O/U) n'avait ce problème, elles étaient déjà toutes gated sur les matchs programmés.

**Correction surconfiance points WNBA (1er août 2026, `backend/compute.js` + miroir `src/pages/BasketballDetailPage.jsx`) :**
Investigation déclenchée par l'utilisateur suite à un pari réel (Arike Ogunbowale, Over 14.5/15.5 pts) : le near-miss montrait le modèle **systématiquement surconfiant** sur les points WNBA à toutes les tranches de probabilité (ex: 65% affiché → 55,6% de réussite réelle, -9,5pp d'écart) — l'inverse exact des rebonds (sous-confiants, d'où le test réussi à 68% du 30 juillet). Deux causes structurelles trouvées, propres aux points (jamais aux reb/ast/tpm) :
- **Cause 1 — un filtre qui cachait les mauvaises soirées** : `calcStd`/`isConsistentStat`/`blendedSeasonAvg`/le calcul EWA de `computeEstimate` excluaient les matchs à 0 pts avec ≥12 min (fautes, tir glacial, sortie précoce) — traités comme des "outliers" à retirer, alors que c'est de la vraie variance à voir. Aucune exclusion équivalente n'existait pour reb/ast/tpm. Fix : filtre retiré, points traités comme les autres stats (`g.min > 10 && g[key] != null`).
- **Cause 2 — l'ancrage volume×efficacité (`getShotVolumeAnchor`, 15 juin) ne touchait que la moyenne, jamais l'incertitude** : ce mécanisme (blend 85/15 avec la projection principale) pousse la moyenne vers le haut pendant une série chaude au tir, mais son signal n'était jamais reflété dans `deviation.pts` (jusqu'ici `|adjMult-1|`, qui ne voit que les facteurs AVANT le blend volAnchor) — donc `probAtLeast` n'élargissait jamais le std en conséquence. Fix : `deviation.pts` recalculée comme l'écart réel final `|projPts/basePts - 1|`, qui capture le mouvement total (adjMult + volAnchor).
- **Deux corrections déjà tentées avant (18-20 juillet, shrinkage pts renforcé à 0.35 vs 0.12-0.25 pour les autres stats, cap adjMult resserré 1.24→1.12) n'avaient pas suffi** — ces deux nouvelles causes sont les vrais points morts non traités jusqu'ici.
- **Garde-fou explicite de l'utilisateur respecté** : aucune des deux corrections ne touche au système de détection "joueuse chaude" (forme récente, EWA, volAnchor lui-même) — la projection continue de monter normalement pendant une série chaude, seule l'honnêteté de la confiance autour change.
- **Miroir frontend** : `calcStd`/le filtre gClean dans `BasketballDetailPage.jsx` corrigés à l'identique (Cause 1). Le frontend n'a pas de `getShotVolumeAnchor`/volAnchor du tout (divergence backend/frontend pré-existante, hors scope ici) donc Cause 2 ne s'y applique pas.

Raisonnement validé avec l'utilisateur : si le joueur clé finit par ne pas jouer, les chances de l'adversaire ne font que s'améliorer par rapport à ce que `computeTeamWinProb` calcule aujourd'hui (qui suppose encore l'équipe au complet tant que rien n'est confirmé Out) — bloquer ce sens-là coûtait un edge réel pour rien. ## Session 2-4 septembre 2026 — Big Five + Brésil migrés de football-data.org vers api-football

**⚠️ Cette section n'avait jamais été écrite avant le 8 septembre 2026** — le code portait déjà toute cette migration (commentaires datés "2 septembre 2026", "cf. plan de migration"), mais ce fichier n'avait pas été mis à jour en conséquence. Reconstituée a posteriori à partir des commentaires du code, après qu'un écart entre ce fichier et le vrai comportement de l'app (jauge de quota FD bloquée sur "—" au Dashboard) ait conduit à donner deux fois de suite une analyse de quota erronée à l'utilisateur dans une session ultérieure — voir `feedback_verify_claude_md_before_architecture_claims` en mémoire.

**Ce qui a changé** : les 5 grands championnats + Brésil (`FB_MIGRATED_LEAGUES = ['ligue1','pl','laliga','bundes','seriea','bresil']`) ne passent plus du tout par football-data.org pour leurs fixtures/classements/résultats/statut live — tout vient désormais d'api-football via une seule fonction partagée, `fetchApiFootballLeagueBundle(leagueKey)` : 2 appels par ligue (`/fixtures?league=&season=&from=(-3j)&to=(+45j)` + `/standings?league=&season=`), cache 30min persisté sur disque (`football_league_bundle.json`). Coût mesuré : 12 appels/ligue×6/rafraîchissement × 48 rafraîchissements/jour ≈ **576 requêtes/jour**, sur le quota `FOOTBALL_API_KEY` (7500/j) — pas `FD_API_KEY`.

- `/api/fd/matches` et `/api/fd/results` (`_getFdLeaguesResults()`) et `_getBresilMatches()` — tous les trois relisent maintenant ce même bundle au lieu d'appeler `fdGet()`. Noms de route/fonction gardés tels quels (`fd`) pour ne pas toucher aux dizaines d'appelants frontend — seule la source change, en silence, côté backend.
- **Statut live sans attendre le TTL 30min** (3 septembre, cas réel Flamengo-Mirassol resté "programmé" en plein match) : `fetchFixtureLiveStatus(fixtureId)` interroge `/fixtures?id=X` ciblé par match (pas `/fixtures?live=all`, qui arrête de renvoyer un match dès qu'il passe FT — 2e bug trouvé le même soir, cas réel Flamengo-Mirassol à nouveau, resté "EN COURS" après la vraie fin). Résultat FT mis en cache définitivement (ne peut plus changer), sinon TTL 45s. Timeout dur 5s (`LIVE_FIXTURE_FETCH_TIMEOUT_MS`) pour que le bouton "Recharger" ne reste jamais bloqué si plusieurs matchs en direct ont besoin d'un check en même temps.
- **Cache externe des routes raccourci 30min→60s** (3-4 septembre) — le TTL réseau réel (30min, dans `fetchApiFootballLeagueBundle`) ne change pas, mais la re-synthèse en mémoire des routes `/api/fd/matches`/`/api/fd/results` repasse plus souvent dessus, pour ne pas garder un score figé jusqu'à 30min après un but (cas réel PSG-Monaco affiché 0-0 alors que le bundle sous-jacent savait déjà 1-0). Zéro coût réseau supplémentaire.
- **Fix settlement 4 septembre** — `_getFdLeaguesResults()` ne rafraîchissait pas le statut en direct avant de conclure, contrairement à `/api/fd/matches` déjà corrigé le même soir : un match resté "programmé" dans le bundle pendant une pause manuelle prolongée ne remontait jamais comme réglable, laissant un pari "accepted" bloqué indéfiniment (cas réel Real Sociedad-Celta BTTS, 100€). Même correctif appliqué : check live ciblé par fixture avant de conclure.
- **Bug de classe entière supprimé** : tout le durcissement "statut Brésil corrompu" (`BRESIL_STATUS_RANK`, `_bresilMatchState`, statut non-régressif) compensait un vrai défaut de football-data.org sur cette compétition précise (champ `status` renvoyé corrompu, score qui repasse à `null` sur un match déjà vu en cours). Retiré avec la migration — api-football renvoie un statut depuis une énumération propre, cette classe de bug ne peut structurellement plus se produire. Seul le garde-fou générique "match resté EN COURS trop longtemps" (`FD_MAX_LIVE_MATCH_MS`) est gardé par prudence.
- **Ce qui reste sur football-data.org** (`FD_API_KEY`, quota séparé 10 req/min, quasi inutilisé au quotidien) : la Coupe du Monde (`/api/fd/worldcup`, compétition terminée, masquée de la Carte du Monde) et 2 routes de secours ponctuelles (`/api/fd/match/:id`, `/api/fd/resolve-legacy-id`, lookup d'un match précis par id FD, appelées rarement). C'est pour ça que la jauge de quota FD du Dashboard affiche "—" en continu : `_captureFdQuota()` ne lit son en-tête que dans `fdGet()`, qui n'est plus jamais appelé par les 6 championnats migrés. **Pas un bug** — reflet honnête d'un quota devenu vestigial.
- **Nettoyage pas terminé** ("étape 4" du plan de migration, citée dans le code mais jamais faite) : du code mort traîne encore — `_applyLiveScoreOverride` (plus jamais appelé), `_liveStatusCache` (vidé par le bouton "Recharger" mais devenu un no-op réel), l'ancien mécanisme de détection de statut corrompu propre au Brésil. Rien de cassé, juste pas encore retiré.

**Pourquoi ça compte pour une extension à de nouveaux championnats** : ce bundle (`fetchApiFootballLeagueBundle`) est exactement le patron à réutiliser tel quel pour tout nouveau championnat foot ajouté à l'app (ex. Grèce/Arabie Saoudite/Turquie/Belgique/Portugal/Pays-Bas, discussion du 8 septembre) — il ne reste donc plus qu'un seul patron d'intégration foot (celui des coupes d'Europe et celui-ci ont convergé), pas deux à choisir entre.

## Session 9 septembre 2026 — % calibré transformé en vrai filtre d'alerte (`CALIB_GATE_FLOOR`)

Déclenché par un cas réel trouvé en creusant l'artifact "Seuils par marché" (voir plus haut) : le Total O/U basket WNBA a enchaîné 18 gagnés/1 perdu (28 juillet-2 août) puis 6 gagnés/15 perdus (3-17 août), toujours sur des candidats "Over" ≥74% — le modèle est resté confiant pendant un vrai ralentissement du rythme de jeu, sans que le seuil brut ne s'ajuste. Demande explicite utilisateur : pas question de mettre en pause d'autres marchés (déjà fait pour DC/team_total/spread/MLB cette semaine) — trouver une solution qui garde les marchés actifs.

- **Le % calibré existait déjà** (`_calibratedProbabilityForAlert`, 7 septembre) mais était **purement informatif** — affiché sur la carte, jamais utilisé pour décider si une alerte part ou non.
- **Nouveau gate** (`_calibGateBlocked`/`_calibBlockFor`, juste après `_calibratedProbabilityForAlert` dans `server.js`) : une alerte candidate est bloquée si le taux de réussite RÉEL observé sur des cas passés à un % brut similaire (le bloc isotonique déjà calculé) tombe sous `CALIB_GATE_FLOOR = 60%` — **à condition** que le bloc ait au moins `CALIB_GATE_MIN_N = 30` cas résolus (sinon gate inactif, pas assez de données pour trancher — évite de bloquer à tort un marché neuf ou une ligue à faible volume, ex. BTTS Ligue 1 qui n'a que 5 cas).
- **Un seul point d'application** : `_calibBlocks` est maintenant calculé **avant** le filtre `filteredAlerts` (déplacé plus haut dans `generateBackgroundAlerts()`, réutilisé tel quel plus bas pour l'affichage `calibratedProbability` — pas recalculé 2 fois) ; le gate s'ajoute au filtre existant de dédoublonnage joueur (`_dedupedAlerts` → `filteredAlerts`), donc actif automatiquement sur **tous les marchés déjà couverts par la calibration** : BTTS/Total/Résultat foot, props WNBA (pts/reb/ast/tpm), Résultat/Total équipe WNBA — sans toucher aux ~15 points d'émission individuels (`newAlerts.push`) qui restent inchangés.
- **Ne touche jamais les alertes déjà acceptées** — le gate s'applique uniquement à `newAlerts`/`filteredAlerts` (candidats du cycle), fusionnés APRÈS avec `_acceptedAlerts` qui reste prioritaire et intact.
- **Auto-correcteur, pas un couperet fixe** : contrairement à une pause ou une suppression de marché, ce plancher se resserre tout seul quand un marché traverse une mauvaise passe (comme la série d'août) et se desserre tout seul dès que la calibration redevient bonne — recalculé à chaque cycle de 20 minutes à partir du near-miss à jour.

## Session 10 septembre 2026 (suite 7) — Cycle bg-alerts figé par une coupure réseau, purge "famille buts" jamais suivie de sa recréation

Signalé par l'utilisateur : impossible d'accepter l'alerte Coritiba-Atletico Paranaense sur Telegram, "alerte introuvable". Pas un bug de token — l'alerte avait réellement disparu côté serveur.

- **Cause immédiate** : le mécanisme "une seule alerte buts par match" (`goalsFamilyChampion`, section BTTS/Total plus haut) compare BTTS et Total par probabilité brute et purge (`_staleAlertIds` → `delete byId[staleId]`, suppression réelle, pas juste `obsolete:true`) le marché perdant. Sur ce match, Total +1,5 est monté à 76% (contre ~55% pour BTTS) — la purge de l'alerte BTTS pending s'est bien exécutée, mais la création de la nouvelle alerte Total (plus bas dans le même bloc `for` par fixture) n'a jamais eu lieu : une vraie coupure réseau côté utilisateur à cet instant précis (DNS MongoDB en échec, `ETIMEDOUT`/`SocketError` vus dans `/api/system/error-log`) a fait planter le reste du traitement de cette fixture, avalé en silence par le `catch` par-fixture (aucune trace de l'échec dans les logs).
- **Aggravant découvert en creusant : le cycle est resté figé indéfiniment** — `generateBackgroundAlertsGuarded()` pose `_bgAlertsInFlight = true` en tête et le remet à `false` dans un `finally`, mais si l'exception réseau a laissé une promesse non résolue (fetch/Playwright sans timeout dur) plutôt que de rejeter proprement, ce `finally` n'est jamais atteint — **plus aucun cycle suivant ne peut tourner** (`generateBackgroundAlertsGuarded()` renvoie immédiatement si `_bgAlertsInFlight` est déjà `true`), et ce jusqu'au redémarrage du process. Confirmé en direct : `bgLastRun`/`alertsPending` ne bougeaient plus du tout malgré un déclenchement manuel (`/api/nba/trigger-alerts`) répété.
- **Fix appliqué (pas un changement de code)** : redémarrage du backend (nodemon a eu besoin d'un `touch server.js` pour redémarrer réellement après un `kill -TERM` — restait sur "aucun process actif" sans ça), puis déclenchement manuel d'un cycle propre. Résultat : `fdbr_1492374_total_1.5` (Over 1,5, 76%, calibré 78,1%) créée normalement, notifiée sur Telegram avec boutons fonctionnels.
- **Pas encore corrigé dans le code** : aucun garde-fou n'existe contre un cycle qui reste indéfiniment "in flight" suite à une promesse jamais résolue — `_waitForBgAlertsCycle()` (30 août) attend la fin d'un cycle en vol mais suppose qu'il finira un jour ; rien ne le fait expirer de force. Un `Promise.race` avec un timeout dur sur `generateBackgroundAlerts()` (comme déjà fait pour `fetchBetclicFootballExtras`, cf. session 23 juillet) préviendrait ce blocage total à l'avenir — pas implémenté cette session, signalé pour référence future.
- **Leçon pour la purge "famille buts"** : la purge (suppression immédiate) et la recréation (plus bas dans le même bloc) ne sont pas atomiques — si le code entre les deux lève une exception, l'alerte purgée n'a aucune chance de revenir avant le cycle suivant (20 min), voire jamais si ce cycle suivant ne se déclenche pas (cf. ci-dessus). Un cas limite à garder en tête si ce genre de "alerte disparue sans raison" se reproduit — vérifier `/api/system/error-log` et `/api/system/health` (`bgLastRun`/`alertsPending` figés) avant de chercher un bug de token Telegram.

**Purge orpheline BTTS frontend limitée à `fd_`/`fdcdm_` (`syncAlerts.js`)** : trouvée en creusant le cas ci-dessus — une alerte BTTS pending sur un championnat ajouté depuis (Brésil, coupes d'Europe, Grèce/Arabie/Portugal) qui disparaît côté backend restait affichée indéfiniment dans l'app (jamais purgée localement), alors que Telegram (qui interroge le vrai état serveur) répondait déjà "introuvable" sur le même message — d'où la confusion "dispo dans l'app mais pas sur Telegram". Contrairement à Total/Résultat (déjà prefix-agnostiques), seule la purge BTTS avait cette restriction, jamais étendue depuis sa création. Fix : nouvelle constante `LIVE_FOOTBALL_FIXTURE_PREFIX` (les 9 préfixes réels) réutilisée à la place du regex figé `/^(fd_|fdcdm_)/`.

**Artifact "Seuils par marché" — Portugal invisible malgré des données réelles** : `FB_LEAGUE_ORDER` (tableau JS figé dans l'artifact lui-même, pilote les onglets de ligue ET le total affiché) n'avait jamais reçu `'Portugal'` lors de son ajout au moteur le 9 septembre — ses candidats existaient dans `DATA` mais restaient invisibles et exclus du total. ## Session 12 septembre 2026 (suite) — Near-miss figé sur la 1ère évaluation, jamais rafraîchi (bug trouvé sur 5 stores)

Signalé par l'utilisateur sur l'artifact "Seuils par marché" : l'alerte BTTS Venezia-Fiorentina, acceptée hier soir à **64%**, apparaissait classée dans la case **54%** du tableau de calibration.

**Cause** : les fonctions de near-miss (`_logFootballNearMiss`, `_logBasketMarketNearMiss`, et les 3 stores V2 — `_logFootballNearMissV2`/`_logBasketMarketNearMissV2`/`_logPropNearMissV2`) écrivaient leur candidat **une seule fois** (`if (store.some(c => c.id === id)) return;`) puis ne le retouchaient plus jamais, même quand le modèle se raffine à chaque cycle de 20 min à mesure que la forme récente/xG se précisent. Résultat : la probabilité gelée dans le near-miss est celle de la **toute première évaluation** (parfois plusieurs jours avant le match), jamais celle qui a réellement gouverné une vraie alerte le jour J — cas mesuré : 54,6% à la première détection → 64% au moment de l'alerte réelle envoyée et acceptée, un écart de 10 points.

**Portée réelle plus large qu'un simple problème d'affichage** : `_logBasketMarketNearMiss` (Résultat/Total équipe basket) alimente aussi `CALIB_GATE_FLOOR` (le gate qui bloque une alerte si la calibration réelle à ce % est mauvaise, 9 septembre) et le "% calibré" affiché sur Telegram — ces deux mécanismes tournaient donc potentiellement sur des probabilités périmées de plusieurs jours, pas sur celle qui gouverne réellement la décision du cycle en cours.

**Fix, appliqué aux 5 stores** : même patron que `_logNearMissCandidate` (props V1, qui faisait déjà ça correctement) — le candidat se met à jour en place (probabilité/floor/cotes/tags/lambdas) à chaque cycle tant que `status === 'pending'`, ne touche plus jamais une fois résolu (won/lost/void). `savedAt` n'est volontairement pas rafraîchi (marque la 1re apparition, sert la fenêtre de rétention 90 jours).

**Correction rétroactive** : l'entrée near-miss Venezia-Fiorentina déjà résolue (`won`) a été patchée manuellement à 64% (valeur réelle de l'alerte acceptée, `bet_ledger.json`) puisqu'un candidat déjà `won`/`lost` n'est plus jamais retouché par le fix ci-dessus — seul ce cas précis nécessitait une intervention manuelle, tous les futurs candidats se corrigeront tout seuls au fil des cycles.

**Règle retenue avec l'utilisateur** : peu importe si un store veut un jour garder un historique de plusieurs valeurs — la probabilité qui compte pour la calibration est **celle en vigueur au moment de la décision réelle**, jamais une valeur de première détection périmée. À appliquer par défaut à tout futur store de near-miss.

**Backtesting — ROI/Win Rate/P&L neutralisés sous 10 paris résolus (`BacktestingPage.jsx`, même session)** : cas réel signalé (4 paris résolus, ROI -16,5% en rouge, lu comme une vraie perte confirmée alors que l'échantillon est minuscule). Décisions successives de l'utilisateur :
- **ROI** : affiché à **0,0% gris neutre** (pas la vraie valeur) sous 10 paris résolus (même seuil que `calcSignificance()`/"Trop peu de données" déjà existant sur la page).
- **Win Rate** : garde sa vraie valeur ET sa vraie couleur (vert ≥50%/rouge sinon) à tout échantillon — 1er essai avait aussi grisé le Win Rate, retour en arrière explicite ("le Win Rate seul n'est pas jugé trompeur, contrairement au ROI qui dépend aussi des cotes").

**Bug Telegram — un accept fait sur le site pouvait être silencieusement écrasé en "rejeté" (cas réels Espanyol, Levante, marché Buts par équipe)** : accepter une alerte depuis le site (`POST /api/accepted-alerts`) ne touchait jamais le message Telegram d'origine ni ses tokens — ses boutons Accepter/Rejeter restaient actifs indéfiniment. ## Adding fixtures or leagues

- **Football static data**: edit `src/utils/fixtures.js`. The `LEAGUES` array controls ordering and accent colors.
- **Basketball static data**: edit `src/utils/basketball.js`. Après chaque modif, mettre à jour ce fichier CLAUDE.md ET `memory/project_nba_data.md`.
- **CONVENTION DATES NBA** : les matchs jouent en ET (UTC-4 en été). Toujours convertir en UTC pour le champ `date` :
  - 20h30 ET → lendemain T00:30:00Z (ex: 25 mai 20h30 ET → `2026-05-26T00:30:00Z`)
  - 21h00 ET → lendemain T01:00:00Z
  - Ne jamais écrire la date ET telle quelle — c'est la source du bug "match détecté terminé avant d'avoir lieu".
- **Live football leagues**: add entries to `FOOTBALL_LEAGUES` (server.js). Odds coverage is automatic — `_mergeFootballBookmaker` scrapes Unibet/Betclic/Winamax/Pinnacle directly and creates a fresh entry for any team-name pair it doesn't already recognize (no per-league config; `ODDS_SPORTS`/The Odds API removed 9 septembre 2026, see session above).
